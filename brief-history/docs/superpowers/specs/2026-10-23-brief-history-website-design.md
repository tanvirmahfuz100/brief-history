# A Brief History of Past Questions — MVP Design

## Purpose

Build a public, mobile-friendly question archive for students in the self-contained
`brief-history/` website project and eventual public repository, with the website
title **A Brief History of Past Questions**.
The first release makes the existing question papers and syllabus material easy to
discover by course, session, exam, and batch context.

The visual direction is editorial and archival: generous whitespace, restrained
typography, dark ink on warm paper-like surfaces, and subtle timeline/scientific
motifs. The reference to *A Brief History of Time* is treated as mood and
information architecture inspiration only; no cover, artwork, or distinctive
protected layout is copied.

## Scope

### In scope

- Public static website deployable to GitHub Pages.
- Responsive homepage introducing the project and the “A Project of Theory of
  Readability” attribution.
- Course-first navigation.
- Course directory with course code, title, department, and available papers.
- Course detail pages with:
  - syllabus content where available;
  - papers grouped by academic session and exam type;
  - clear links to individual paper pages.
- Individual question-paper pages rendered from normalized Markdown content.
- Client-side search/filtering by course, session, exam type, and paper title.
- Accessible semantic HTML, keyboard navigation, readable contrast, responsive
  layout, and reduced-motion support.
- Content validation during build so malformed front matter or missing required
  fields fails clearly.
- A documented content schema that can later support answers, references, videos,
  analytics, PDF exports, and watermarking without changing the paper identity model.

### Out of scope for the MVP

- User accounts, comments, or moderation workflows.
- Answers generated by AI or copied from books.
- YouTube embeds and topic-level learning resources.
- Book/page references.
- Teacher-level or question-pattern analytics.
- Server-side search, database storage, or an administrative CMS.
- PDF generation and watermarking.
- OCR correction tooling; existing Markdown remains the source content for this
  milestone.

## Recommended architecture

Use **Astro** with a static output target for GitHub Pages.

- `brief-history/src/content/questions/`: normalized question-paper Markdown files.
- `brief-history/src/content/syllabi/`: syllabus Markdown or structured data by course.
- `brief-history/src/content/config.ts`: typed content collections and required front matter.
- `brief-history/src/pages/`: homepage, course directory, course detail, and paper routes.
- `brief-history/src/components/`: navigation, filters, paper metadata, question rendering,
  syllabus sections, and shared layout components.
- `brief-history/src/styles/`: design tokens and responsive styles.
- `brief-history/scripts/`: import/normalization and validation utilities kept separate from
  runtime page components.
- `brief-history/.github/workflows/`: build and deploy to GitHub Pages.

The current root-level `ocr/incoming/*.md` files are an ingestion source, not the
final web content location. An import step should copy or transform them into the
`brief-history` content collection while preserving the original `source_id`,
source file, page list,
confidence, notes, and paper metadata. The original OCR files remain untouched.

## Content model

Every question paper must have:

- stable `source_id`;
- `source_file`;
- `pages`;
- university and department;
- course title and course code;
- year/semester;
- exam and session;
- time and full marks when known;
- instructions and choice text;
- OCR confidence and notes.

The content layer should derive:

- normalized course slug;
- session label;
- exam slug;
- paper display title;
- searchable text;
- source-page links for internal provenance where appropriate.

Unknown values remain explicitly unknown or empty; the build must not invent
metadata. Low-confidence papers display a visible transcription note rather than
silently presenting uncertain text as authoritative.

Future optional fields:

- `topics`;
- `teacher`;
- `references`;
- `videos`;
- `answers`;
- `download`;
- `watermark`.

These remain optional and unused in the MVP.

## Navigation and user flow

1. **Home**: project statement, featured course count, recent/available sessions,
   and a prominent “Browse courses” action.
2. **Courses**: searchable/filterable directory organized primarily by course.
3. **Course page**: course identity, syllabus, session/exam grouping, and paper
   cards.
4. **Paper page**: metadata summary, confidence/provenance notice when needed,
   rendered Markdown questions, and back links to the course and course index.

The URL structure should be stable and human-readable:

- `/`
- `/courses/`
- `/courses/<course-slug>/`
- `/courses/<course-slug>/<paper-slug>/`

## Visual system

- Warm paper background with dark ink text and one restrained accent color.
- Serif display type for the title and section headings; highly legible sans-serif
  or humanist text for controls and metadata.
- A “timeline” treatment for sessions without turning the site into a decorative
  animation.
- Wide readable measure for question text; tables must scroll horizontally on
  narrow screens rather than collapse data.
- Clear distinction between archival content, metadata, and navigation.
- No reliance on color alone for confidence, exam type, or selected filters.

The design should prioritize reading over spectacle. Motion is optional, subtle,
and disabled under `prefers-reduced-motion`.

## Data flow and error handling

1. Import/normalize source Markdown.
2. Validate front matter and required relationships.
3. Build typed content collections.
4. Generate static routes and search index.
5. Fail the build with file path and field-specific errors when content is invalid.

Missing optional content produces an explicit empty state, such as “Syllabus not
available yet,” rather than a broken link or fabricated placeholder content.
Malformed Markdown should be reported during build; the site must not silently
drop a paper.

## Testing and acceptance criteria

- Build succeeds from a clean install.
- Every current OCR paper either imports successfully or is listed in a
  field-specific validation report.
- Course directory contains every normalized course represented by the imported
  papers.
- Every paper has a reachable detail route and correct course/session/exam metadata.
- Syllabus links resolve where syllabus content exists.
- Search/filtering returns the expected paper for course, session, and exam terms.
- Responsive layouts work at narrow mobile and desktop widths.
- Keyboard focus is visible and all interactive controls have accessible names.
- No horizontal overflow occurs except intentionally scrollable data tables.
- GitHub Pages base-path configuration works for the public repository name
  `brief-history`.

## Delivery slices

1. Repository/app foundation, Astro configuration, design tokens, and deployment
   skeleton.
2. Content import and validation for OCR papers and syllabus files.
3. Course directory, course pages, and paper routes.
4. Responsive editorial UI and client-side filtering.
5. Accessibility checks, build validation, and GitHub Pages workflow.

Each slice should be tested and committed separately. The MVP is complete when
all five slices build and deploy from the public repository without manual content
editing in generated output.
